# エディタコンポーネントの比較検討

OREO (**Overpowered Rich Editor for Overlords**) の核となる、テキスト表示・編集領域の基盤コンポーネント候補の比較です。
「シンプル・ミニマル」な外観と「高いリソース効率」という相反する目標を達成するための最適な選択肢を検討します。

## 1. 候補一覧と特徴

| 候補 | 開発元/基盤 | 主な特徴 | メリット | デメリット |
| :--- | :--- | :--- | :--- | :--- |
| **JavaFX TextArea** | 標準ライブラリ | シンプルなプレーンテキスト用。 | 軽量、標準搭載。 | 文字ごとのスタイル不可。巨大ファイルの描画に限界。 |
| **RichTextFX** | コミュニティ | JavaFX でのコードエディタの標準。 | 高度な装飾、行番号、仮想スクロール対応。 | 依存ライブラリの追加。メモリ管理に注意が必要。 |
| **Monaco Editor** | Microsoft (WebView) | VS Code のエディタエンジン。 | 最強の編集機能、LSP との親和性が最高。 | WebView (WebKit) のオーバーヘッド大。メモリ消費激しい。 |
| **CodeMirror 6** | コミュニティ (WebView) | モダンな Web ベースエディタ。 | Monaco より軽量・モジュール化されている。 | WebView 依存は変わらず。 |
| **Custom Implementation** | 独自 (Canvas/TextFlow) | 必要な機能のみを実装。 | 理論上、最高のリソース効率と自由度。 | 開発コストが極めて高い（数人月〜）。 |

---

## 2. 詳細分析

### 2.1 表現力の顕著な例 (Expressiveness Examples)

各コンポーネントにおける表現力の違いが最も顕著に現れる例を以下に示します。

| 比較項目 | TextArea (標準) | RichTextFX (ネイティブ) | WebView (Monaco/CodeMirror) |
| :--- | :--- | :--- | :--- |
| **文字ごとの装飾** | 不可（全体一律） | 可能（部分的な色・太字等） | 極めて高度（CSS をフル活用可能） |
| **インライン画像・ボタン** | 不可 | 可能（テキスト内に Node を挿入） | 可能（HTML 要素として自由自在） |
| **シンタックスハイライト** | 正規表現による簡易的なものも困難 | 高速なリアルタイム強調が可能 | LSP 連携による完璧なセマンティック強調 |
| **複雑なレイアウト** | 単一列のみ | 行ごとのカスタム背景やガター | CSS Grid/Flexbox を用いた多機能 UI |
| **高度なタイポグラフィ** | OS 標準に従う | 合字（Ligatures）等の制御が可能 | ブラウザエンジンの全機能（WebFont等） |

### 2.2 JavaFX TextArea (現状採用)
- **用途**: 設定画面のテキスト入力や、単純なメモ。
- **リソース効率**: 非常に高い。JavaFX の標準シーングラフで完結。
- **OREO への適合性**: 基本的な編集には十分だが、「条件付きスタイル（シンタックスハイライト）」の実現には機能不足。

### 2.2 RichTextFX (有力候補)
- **用途**: IDE、コードエディタ、マークダウンエディタ。
- **リソース効率**: `VirtualizedScrollPane` を利用することで、数万行のファイルでも表示されている部分のみを描画可能。
- **OREO への適合性**: バランスが最も良い。JavaFX ネイティブであるため、OS 非依存の描画一貫性を保ちやすい。

### 2.3 WebView ベース (Monaco / CodeMirror)
- **用途**: クラウド IDE、ブラウザベースのエディタ。
- **リソース効率**: 低い。Java 内部でブラウザ（WebKit）を走らせるため、1タブごとに数十〜数百 MB のメモリを消費する。
- **OREO への適合性**: 「メモリ使用量を抑える」ポリシーに反する。ただし、LSP 連携などの開発補助機能が極めて重要な場合は検討の余地あり。

### 2.4 カスタム実装 (Canvas)
- **用途**: Sublime Text や IntelliJ (Swing) など。
- **リソース効率**: 最高。テキストの配置計算から描画まで自前で行う。
- **OREO への適合性**: 理想的だが、アクセシビリティ（IME、スクリーンリーダー）や複雑な文字（絵文字、双方向テキスト）の対応を自前で行うのは現実的ではない。

## 3. プレビューコンポーネントとの連動

Markdown プレビュー機能に WebView を採用するかどうかが、エディタコンポーネントの選定にも影響を与えます。詳細は [Markdown プレビューの実現方式検討](Markdown-Preview-Implementation.md) を参照してください。

- **WebView を採用する場合**:
    - エディタコンポーネントとして Monaco や CodeMirror を採用する際の「メモリ消費」というデメリットが、プレビュー用 WebView とリソースを共有（あるいは重複を許容）することで相対的に軽減される可能性があります。
- **Native Rendering を採用する場合**:
    - エディタも `RichTextFX` 等の JavaFX ネイティブなコンポーネントを採用することで、アプリケーション全体として極めて低いメモリフットプリントを維持できます。

---

## 4. 推奨される選択肢

OREO のコンセプトである「Overpowered (高効率)」を達成するため、以下のステップでの移行を提案します。

1.  **短期目標**: `RichTextFX` への移行。
    - 実装コストを抑えつつ、シンタックスハイライトと行番号の完全な同期を実現。
2.  **長期目標**: `RichTextFX` をカスタマイズし、Piece Table 等のデータ構造と統合。
    - データ保持層を Piece Table に置き換えることで、大規模ファイルでのメモリ消費をさらに最適化する。

# Markdown プレビューの実現方式検討

Markdown のプレビュー表示を実現するための技術選定に関する比較検討です。
OREO のコアポリシーである「リソース効率（メモリ使用量抑制）」と、プレビューの「再現性・表現力」のバランスを評価します。

## 1. 候補一覧

| 候補 | 分類 | メリット | デメリット | リソース効率 |
| :--- | :--- | :--- | :--- | :--- |
| **JavaFX WebView** | ブラウザエンジン (WebKit) | HTML/CSS をそのまま利用可能。再現性が極めて高い。 | メモリ消費が非常に大きい。1インスタンスで数百MB。 | 低 |
| **Native Node Rendering** | JavaFX Node への変換 | ブラウザエンジン不要。メモリ消費が極めて少ない。 | 実装コストが高い。テーブルや複雑なレイアウトの再現が困難。 | 高 |
| **RichTextFX (Read-only)** | テキスト装飾 | エディタと基盤を共通化できる。非常に軽量。 | 画像の配置やブロック要素のレイアウトに限界がある。 | 高 |

---

## 2. 詳細分析

### 2.1 表現力の顕著な例 (Expressiveness Examples)

レンダリング方式による表現力の差は、特に以下の要素で顕著になります。

| 要素 | WebView (ブラウザ) | Native Node (JavaFX) | RichTextFX (テキスト) |
| :--- | :--- | :--- | :--- |
| **テーブル (Table)** | 複雑な結合、セル内折り返しも完璧。 | 基本的な格子状は可能だが、複雑なレイアウトは困難。 | タブによる簡易的な整列に限定される。 |
| **数式 (Math)** | MathJax/KaTeX 等で美麗に描画。 | 特殊なフォントや Node 構築が必要で、実装難易度が高い。 | 不可能。 |
| **図表 (Diagram)** | Mermaid 等の JS ライブラリで描画可能。 | 画像として出力されたものしか表示できない。 | 不可能。 |
| **CSS デザイン** | GitHub 等の既存テーマがそのまま使える。 | JavaFX CSS で一から構築が必要。 | テキスト装飾（色・太字）のみ。 |
| **インタラクティブ性** | 動画埋め込み、アコーディオン等が可能。 | 基本的に静的な描画に限定される。 | なし。 |

### 2.2 JavaFX WebView
- **仕組み**: `flexmark-java` 等で Markdown を HTML に変換し、`WebView` に流し込む。
- **再現性**: 既存の CSS フレームワーク（GitHub スタイル等）を流用でき、最強。
- **リソース効率**: WebKit エンジンが動作するため、単一のテキストエディタとしては過剰なリソースを消費する。「メモリ使用量を抑える」ポリシーには最も反する。

### 2.2 Native Node Rendering (推奨案)
- **仕組み**: Markdown を AST (抽象構文木) に変換し、`TextFlow`, `VBox`, `ImageView` 等の JavaFX コンポーネントに1対1で変換して描画する。
- **再現性**: スタイルは JavaFX CSS で定義する。基本的な装飾（太字、リンク、リスト）は容易だが、複雑なテーブルや埋め込みコンテンツの対応には開発工数が必要。
- **リソース効率**: 非常に高い。JavaFX のシーングラフに直接統合されるため、メモリ消費は通常の UI コンポーネントと同等。

### 2.3 RichTextFX (Read-only)
- **仕組み**: エディタで使用する `RichTextFX` を読み取り専用モードでプレビューとして使用する。
- **再現性**: シンタックスハイライトに近いレベルの装飾に限定される。
- **用途**: コードスニペットの簡易確認などには適しているが、完全な Markdown プレビューとしては力不足。

## 3. エディタコンポーネントへの影響

プレビュー機能に **WebView が不可避であると判断される場合**、以下の再検討が必要です。

1.  **WebView ベースエディタ（Monaco等）の再評価**:
    - プレビューのために WebView を常駐させるのであれば、エディタ自体も WebView ベースにすることで、エンジンのメモリを共有（または同一プロセス内で管理）し、機能性の向上（LSP連携等）を優先する選択肢が浮上する。
2.  **プロセスの分離**:
    - プレビュー時のみ WebView プロセスを起動し、非表示時は破棄するなどの動的な管理。

---

## 4. 結論と方針

OREO のアイデンティティを維持するため、以下の優先順位で検討を進めます。

1.  **第一候補: Native Node Rendering**
    - `flexmark-java` をベースに、JavaFX Node へ変換する軽量なレンダラーを試作する。
    - これにより、プレビュー中も低メモリ消費を維持する。
2.  **第二候補: WebView (オンデマンド起動)**
    - Native 方式での表現力が不足する場合のみ採用するが、プレビューがアクティブでない時は WebView インスタンスを破棄する設計とする。
